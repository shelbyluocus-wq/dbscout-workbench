# Project Performance Optimization Design

- 日期：2026-07-10
- 分支：main
- 状态：已通过规格自审，待用户 review
- 来源：用户要求“彻底详细地分析项目，优化软件性能，让软件更加快速不要卡”，并授权按全项目性能专项方式推进

## 1. 目标

把 DB Scout Workbench 做成“打开更快、搜索更快、滚动更稳、长操作不假死”的桌面工作台，而不是只修某一个点的卡顿。

本轮专项的核心目标不是追求抽象跑分，而是提升用户最容易感知到的四类体验：

1. 打开数据库主页、打开表、切换标签页时更快进入可用状态。
2. 大表滚动、选中、编辑、跳转时不明显掉帧、不闷住。
3. 表内搜索、值搜索、Ctrl+P 等高频检索路径更快给出结果或明确进度。
4. 首页、侧边栏、批量操作等“不是崩溃但像卡死”的链路，改成渐进式反馈而不是一口气堵住界面。

## 2. 成功标准

本轮以“体感改善”作为第一验收标准，配合可采集的指标做辅助判断：

### 2.1 用户体感标准

- 打开一个真实大表时，应先尽快看到首屏数据，再逐步补齐总数、统计或次级信息。
- 在已加载的大表里滚动和连续选中时，不应出现持续性的卡顿、掉帧或明显输入延迟。
- 搜索输入后，应先快速看到首批命中、正在搜索状态或剩余扫描进度，不能长时间无反馈。
- 首页和侧边栏面对较多表时，应先展示可交互骨架或首批内容，而不是整页一起闷出来。
- 批量导入、导出、值搜索等长操作不能表现成“软件像没响应”，必须持续更新阶段或进度。

### 2.2 指标辅助标准

- 关键链路都能留下统一的开发期性能标记，能对比优化前后。
- 主线程重活尽量拆散，避免一次性同步工作导致长时间阻塞。
- 重复打开同一类页面、重复执行同一搜索时，应更多复用已得出的结果，而不是从头做完整重算。

## 3. 已知现状与热点判断

结合现有代码、近期提交和仓库中的在制改动，可以把当前热点归纳为五组。

### 3.1 打开表的“首屏快”和“完整信息慢”仍需继续解耦

项目已经有一轮正确方向的优化：打开表时先拿首批 rows，再异步补精确总数与侧边栏 schema。这说明“先显示可用内容、再补全次级信息”已经成为正确路线。

但从当前结构看，打开表仍可能被以下附加工作拖慢体感：

- 打开后立刻连带触发 schema 刷新、总数刷新、状态更新、自动列宽等后续动作。
- tab 切换和分屏场景下，非当前焦点页签也可能继续消耗计算和异步资源。
- 某些只影响“更完整信息”的逻辑，仍然过早进入首屏关键路径。

因此，表打开链路需要继续做“关键路径瘦身”。

### 3.2 表格渲染已做虚拟滚动，但单个可见单元格的重复工作仍偏多

当前数据表已经做了纵向虚拟滚动，这是正确基础；但热点不只在“渲染多少行”，还在“每个可见单元格渲染时做了多少重复计算”。

典型成本包括：

- 同一批可见单元格内重复做列名标准化、行主键构造、命中高亮判定、错误/待保存状态查询。
- 滚动时同时触发可见区更新、更多数据判定、搜索命中联动等多条计算链。
- 某些只对当前焦点行/列有价值的逻辑，仍按整块可见区域重复执行。

这会直接影响“滚动不顺”“移动选择框发涩”“搜索命中时更卡”的问题。

### 3.3 搜索链路已经有局部优化，但仍需要统一成“增量 + 缓存 + 明确反馈”模式

近期已有表内搜索和 value search 的性能修复经验，方向也很明确：不要重复扫描已扫过的数据，不要保留已经失效的整表旧路径。

本轮需要进一步统一几个原则：

- 同一查询重复导航命中时，不应从头重新扫一遍。
- 搜索输入时先走轻路径（精确、前缀、包含），再决定是否进入更重的模糊匹配。
- 高亮渲染不要为了“判断是否命中”和“生成高亮 HTML”重复做两次昂贵计算。
- 跨表值搜索、Ctrl+P 结果页打开、命中跳转要把“结果可见”和“落点准确”同时当成性能目标，而不是只管找到表。

### 3.4 数据库首页与侧边栏已经开始做懒加载，但仍可能在大列表下形成整页重算

最近刚有一笔“lazy load home table metadata”的提交，同时工作区里也存在数据库首页相关的未提交改动，说明这一块正处于演进中。

这部分的性能风险主要不在单个接口，而在“列表一大时，筛选、排序、选择、状态文案、快捷键提示等一整串 computed/watch 一起重算”。

需要把首页/侧边栏处理成：

- 先交付可操作的轻量列表；
- 再按需补评论、字段数、最近访问等附加信息；
- 大量表时尽量只更新可见区或受影响的局部状态；
- 避免一次搜索或一次选中把整页卡片全部重新整理一遍。

### 3.5 长操作的“像卡死”问题，本质上是性能问题而不是纯文案问题

在这类桌面工具里，很多用户说“卡”，并不是 CPU 永远打满，而是：

- 搜索开始了但没有反馈；
- 批量操作在跑但页面完全不动；
- 某个阶段正在等待数据库或磁盘，但界面没有阶段提示；
- 看起来像死机，其实只是主线程被一段同步工作堵住了。

因此，本轮会把“进度、阶段、可取消性、分批让出主线程”当作性能设计的一部分，而不是事后补提示。

## 4. 设计原则

1. **先让用户可操作，再补完整信息。** 首屏、首批结果、首个可交互状态优先于精确总数和完整元数据。
2. **只对可见内容付费。** 只要用户暂时看不到，就不应该抢占关键渲染路径。
3. **同一结果尽量只算一次。** 搜索命中、行标识、列归一化、高亮结果等都应尽量复用。
4. **主线程不要长时间连做重活。** 能拆分的就拆分，能延后的就延后，能分批的就分批。
5. **性能优化不能牺牲现有正确性。** 编辑、撤销、插入行、分屏、搜索落点、只读限制等行为不能因为提速而变形。
6. **先做高收益低风险，再做结构级优化。** 不为了“看起来很高级”而过度改造。

## 5. 方案选择与结论

本轮采用“全链路性能专项治理”，而不是只修前端或只修后端。

### 5.1 不采用“只做前端轻量提速”的原因

只做前端微调虽然风险低，但如果真实瓶颈在打开链路、搜索扫描、后台请求粒度或元数据加载路径，就只能缓解，不会根治。

### 5.2 不采用“只做后端提速”的原因

只优化数据库读取和搜索，也不能解决渲染路径、虚拟滚动、首页列表重算、长操作无反馈造成的主观卡顿。

### 5.3 最终采用的方案

采用“四大体验面 + 一条测量主线”的全链路专项：

1. 打开与切换
2. 搜索与定位
3. 表格交互
4. 首页与侧边栏
5. 统一性能测量与验证

## 6. 详细设计

### 6.1 第一层：先补齐统一性能测量，避免盲改

在当前已有 `performanceMarks` 基础上，把关键用户链路统一打点，确保可以对比优化前后：

- 数据库主页打开开始/首个可交互时刻/附加元数据补齐完成
- 打开表开始/首屏表格可见/精确总数回填完成
- 表格滚动可见区更新/加载下一页触发/下一页合并完成
- 表内搜索开始/已加载数据扫描完成/全量扫描完成/首个命中可跳转
- 值搜索开始/阶段进度更新/结果列表首屏可见
- Ctrl+P 打开/候选列表可见/选中项落点完成

这层不改变产品行为，但会决定后续优化优先级。没有这层，后面的优化很容易靠感觉做，最后只是在“换一种卡”。

### 6.2 第二层：继续瘦身“打开表 / 切换页签”关键路径

核心目标是：让用户尽快看到首屏数据，而不是等所有附加动作都做完。

具体策略：

- 保持“首批数据优先、精确总数后补”的方向，不让总数统计重新回到关键路径。
- 把只影响侧边栏刷新、完整 schema、辅助状态文案、次级视觉增强的逻辑延后到首屏之后。
- 严格取消失焦 tab、旧 session、旧筛选条件触发的过期异步回填，避免看不见的页面还在烧资源。
- 对切换页签、分屏切换时的联动 watcher 做收敛，避免 A 页切换时 B 页还跟着做重算。
- 自动列宽、搜索高亮、冻结提示等非首屏硬依赖能力，优先改为首屏之后再渐进完善。

### 6.3 第三层：压缩表格可见区内的重复工作

虚拟滚动已经保证“不是所有行都渲染”，下一步要保证“渲染出来的那点内容也别反复算”。

具体策略：

- 为当前可见区预先准备轻量的行元数据，如行 key、已归一化列名、必要的命中摘要，避免模板中重复调用。
- 把“命中判断”和“高亮内容生成”尽量合并成一次结果，避免相同单元格做两次重计算。
- 把滚动事件本身保持得足够轻，只更新滚动坐标；把“是否该加载更多”等附加判断放到更合适的调度阶段。
- 对只和当前选中单元格、当前高亮单元格相关的状态，限制其传播范围，不要整屏响应。
- 对宽表场景，避免因为整列状态计算过重而削弱虚拟滚动收益。

### 6.4 第四层：把搜索统一为“先快反馈，再渐进补全”

本轮把所有搜索相关链路统一到同一个体验原则：

- 用户输入后，先快速给出已知命中、轻量排序结果或明确的“正在继续找”；
- 不允许长时间无反馈；
- 对同一查询的重复跳转、重复翻页、重复打开结果页，要尽量复用之前的扫描成果。

具体策略：

- 表内搜索继续使用查询签名和扫描进度缓存，避免已加载数据的重复扫描。
- 更重的模糊匹配放到轻匹配之后，优先保障响应速度。
- 搜索结果命中元数据要能直接支撑“落到第几个命中的具体单元格”，减少跳转前的二次重算。
- Ctrl+P / 值搜索 / 结果页打开之间，明确区分“候选列表可见”“结果页打开”“命中单元格落点完成”三个阶段，分别提速。
- 跨表值搜索继续保留进度事件，并在确认连接池和数据库负载可控后，再考虑谨慎引入有边界的并行扫描。

### 6.5 第五层：数据库首页与侧边栏改成真正的渐进式列表

首页与侧边栏的优化目标不是把所有信息都更早算出来，而是把“能立即操作的部分”更早给用户。

具体策略：

- 延续最近的首页 metadata lazy load 方向，把表列表拆成“轻量身份信息”和“附加说明信息”两层。
- 先渲染表名、基础选择能力、基础打开能力；字段数、注释、最近访问等附加信息按需补齐。
- 排序和筛选时，尽量复用已归一化的表数据，避免每次输入都重新做整表级整理。
- 选择态、快捷提示、状态文案等局部 UI 只在受影响区域更新，不让它们连带整个表列表一起重排。
- 当表数量很多时，优先考虑可见区渲染或分批注入，而不是让整页卡片同帧落地。

### 6.6 第六层：把“长操作不卡死”做成统一交互规范

本轮不把进度提示当作 UI 点缀，而是当成性能设计的一部分。

统一规则：

- 长于一个短交互周期的任务，都要有阶段或进度。
- 能分批推进的任务必须分批，让界面有机会刷新。
- 能取消或能提前结束的搜索/加载任务，不继续做无意义尾活。
- 状态文案要描述任务所处阶段，而不是只显示一个笼统 loading。

适用范围包括：值搜索、批量导入导出、数据库首页补元数据、精确总数回填、可能的大批量 schema 读取等。

## 7. 实施顺序

### Wave 1：性能体检与基线

- 统一关键链路打点
- 跑一次 mock + 当前可用真实链路的基线观察
- 形成“最影响体感的前三类瓶颈”清单

### Wave 2：打开与切换关键路径提速

- 压缩首屏前的附加工作
- 收紧过期异步回填
- 把次级信息后移到首屏之后

### Wave 3：表格渲染与搜索热路径提速

- 压缩可见区重复计算
- 搜索缓存和高亮缓存进一步统一
- 滚动与加载更多调度瘦身

### Wave 4：首页与侧边栏渐进式列表

- 继续完成首页 metadata lazy load 方向
- 降低整列表重算频率
- 让大列表先可用、再补细节

### Wave 5：长操作反馈统一与回归收口

- 补齐阶段/进度/取消能力
- 删除或收敛已确认多余的旧路径
- 做回归验证，防止优化后出现功能回退

## 8. 边界与风险控制

### 8.1 不做的事

- 不为了性能把现有编辑、撤销、插入、只读保护、命中落点这些正确性行为改坏。
- 不在没有证据的情况下大规模重写网格或状态架构。
- 不把本轮变成纯视觉改版或 unrelated 功能重构。
- 不强行把所有搜索都改成激进并发，避免给 MySQL/ClickHouse 带来额外压力。

### 8.2 当前工作树约束

仓库里已经存在数据库首页相关的未提交改动，因此实施时必须遵守：

- 只在确认收益明确时继续沿着这条线增强；
- 避免把在制首页改动整体推翻；
- 与当前需求无关的本地改动不混入同一提交；
- 如果某个高收益性能修复必须碰到这批文件，要以最小改动方式叠加。

## 9. 验证方案

### 9.1 自动化验证

按本仓库习惯使用显式验证栈：

- `node --test src/workbench`
- `cargo test --manifest-path src-tauri/Cargo.toml`（涉及 Rust/backend 时）
- `npm run build`
- `git diff --check`

必要时补充针对性能结构的回归测试，例如：

- 打开表时总数是否仍异步回填
- 搜索缓存是否避免重复扫描
- 可见区元数据是否按 slice 复用
- 首页大列表是否保持渐进式注入或延后补元数据

### 9.2 实机验证

测试通过不代表不卡，因此必须补实际验证：

- 打开数据库主页，确认首批列表是否更早可交互
- 打开较大表，确认首屏数据是否先出来
- 连续滚动、选中、搜索，确认没有新的明显掉帧
- 触发值搜索/批量链路，确认有持续进度或阶段反馈
- 若 dev server 端口变化，按实际打印地址做浏览器/桌面 smoke

## 10. 验收标准

当以下结果同时满足时，本轮专项才算完成：

1. 用户最容易感知的链路——打开、搜索、滚动、首页——至少有一轮明确提速，不是只修边角。
2. 优化建立在可对比的测量结果上，而不是纯主观猜测。
3. 长操作不再表现成“软件像卡死但不知道在干什么”。
4. 自动化验证和实机验证都通过，没有引入新的明显行为回退。
5. 与当前数据库首页在制改动保持兼容，没有把 unrelated 本地修改混进性能专项。
